## Changes

### scripts/schema.sql
- Added `xrtg_routing` (routing control table: table name -> dbKey) and `ttst_test` (multi-database routing test table) definitions.

### src/tables/db.ts
- Reworked from a single module-level connection into a per-dbKey connection registry (`getRawHandler`), keyed `'primary'` (→ `POSTGRES_URL`) or any other dbKey, used as the literal env var name to read (→ `process.env[dbKey]`), each lazily created and cached — Neon `Pool` (one per dbKey) on the Vercel branch, ephemeral `Client` per query on the local branch, same as before per dbKey.
- Follow-up during testing: changed `rtg_dbkey` from a bare suffix (concatenated as `POSTGRES_URL<dbKey>`) to the literal env var name, per explicit user request — more explicit, and any future env var name works with zero code change since the routing row value IS the env var name.
- Added `resolveDbKey`/`getRoutingMap`/`loadRoutingMap`: the `table → dbKey` map loads once per warm instance from `xrtg_routing`, queried directly against the primary raw handler (bypassing routing, since routing itself can't be routed). Any failure — most commonly `xrtg_routing` not existing yet in a given consuming project — falls back to an empty map, so every table resolves to primary exactly as before.
- `sqlHandler.query` now resolves the target dbKey from `table` (already passed by every `table_*` function) before executing, so no other file needed to change. Logging and error-handling (`write_logging` on failure) is unchanged, just centralized into the single unified query path instead of being duplicated per branch.
- Minor, inconsequential behavior note: the unused-in-practice `functionName` fallback label changed from branch-specific `'Neon_Unknown'`/`'localhost_Unknown'` to a single `'Unknown'`, since the branch decision moved into `getRawHandler` — no caller currently omits `functionName`.

### src/tables/tableGeneric/*.ts (all 17 functions)

- `table_write`, `table_update`, `table_upsert`, `table_delete`, `table_count`, `table_check`, `table_duplicate`, `table_drop`, `table_truncate`, `table_copy_data`: previously threw on failure; now catch internally (as they already did to log) and return `TableResult<T>` instead — same `write_logging` calls as before, just returned instead of thrown.

database (`nextjs_shared_test1`), not on primary — simulating a table that's been fully relocated

demonstrates why the routing row is necessary.

## Consuming-project impact — significant, read before reinstalling anywhere

`table_write`/`table_update`/`table_upsert`/`table_delete` no longer throw, and every function's
return shape changed to `TableResult<T>`. This is a breaking change reaching every consuming
project that calls any of the 17 `tableGeneric` functions — grepped for actual usage (excluding
node_modules) just before this plan was written:

| Project | Files using these functions |
|---|---|
| chess | 17 |
| infostore | 4 |
| next-bridge | 27 |
| next-bridgeschool | 75 |
| next-dbadmin | 0 — unaffected |
| richard-dashboard | 0 — unaffected |

That's 123 files across 4 projects that will fail to compile the moment they reinstall a
nextjs-shared version containing this change, until each call site is updated to the new
`{ ok, data, error }` pattern documented in `CONSUMING_PROJECTS.md` section 5. **Do not run the
normal reinstall-in-every-consuming-project release step for this change** — that would break all
four immediately. Recommended sequencing: pin each of the 4 affected projects to the
current (pre-this-change) nextjs-shared version via the Versions tab at `localhost:3009/owner`
until that project's own Claude Code session has migrated its call sites, then unpin one project
at a time. This needs a decision from the user on order/timing before `#commit` — not something to
decide silently here.
